# Модуль «Залог / Выкуп» — ломбард CRM

Внутренняя CRM: NestJS + PostgreSQL/TypeORM API и Vite React SPA (Ant Design, Redux, Tailwind).

Так как любой проект я делаю так, что бы он всегда мог использоваться в production - сюда была заложена **мощная** модульная архитектура, которая позволяет сверху "наращивать" различные блоки на так называемый "скелет" проекта.
По времени данный проект занял **значительно** больше, чем 3 часа: итоговое время равно примерно **восьми часам**, львиная доля из которых заняла на построение архитектуры приложения и реализации общего DTO-слоя с нуля.

## Стек

- **API:** NestJS, TypeORM, Yup DTO, Winston logger, moment-timezone
- **БД:** PostgreSQL `pawnshop_test`, схемы `catalog` / `client` / `pledge`
- **Web:** React (FC), Redux Toolkit, Ant Design, Tailwind
- **Тесты:** Jest + supertest, in-memory **sqljs**
- **TypeScript:** `strict`, ESM (`import`), `emitDecoratorMetadata` для Nest/TypeORM

## Быстрый старт

```bash
cp .env.example .env
npm install
```

### PostgreSQL (внешний)

Укажите доступ к БД в `.env` (`DB_HOST`, `DB_PORT`, …), затем:

```bash
npm run migration:run
npm run seed
npm run dev:api
npm run dev:web
```

- API: http://localhost:3001/api/v1  
- Web (dev): http://localhost:3017 (прокси `/api` → API)  
- Production (compose): API **3019** (`APP_PORT` в `.env` на VPS, `network_mode: host`), web **4001**

### Тесты

```bash

```

Изоляция БД: `DB_TYPE=sqljs`, `synchronize: true`, `clear()` + seed в `beforeEach`. E2e по модулям: `api/src/tests/{catalog,client,pledge}`. Миграции и PG-схемы в e2e не "гоняются".

## Формула выкупа

```
проценты = суммаЗайма × ставкаЗаПериод / 100
         + (если сейчас > дата«до»)
           суммаЗайма × ставкаПросрочки / 100 × числоПериодовПросрочки

суммаВыкупа = суммаЗайма + проценты
```

где `числоПериодовПросрочки` = округление вверх (`дниПросрочки / длинаПериодаПросрочки`).

### Зачем базовая ставка и зачем просрочка

Ломбард выдаёт деньги под залог вещи на оговорённый срок («до» такой-то даты). За пользование деньгами в этот срок клиент платит **базовый процент** — фиксированную плату за весь договорной период (не «за каждый день», а один раз за срок тарифа).

Если клиент не выкупил вещь вовремя, ломбард продолжает нести риск и не может свободно распоряжаться предметом залога. Поэтому сверх базового процента начисляется **плата за просрочку**: стимул вернуть деньги скорее и компенсация за каждый начатый период после даты «до».

Аналогия из жизни: аренда квартиры до 31 марта — фикс за месяц. С 1 апреля жильё уже «не по договору»: обычно считают неустойку/суточные за каждый день или блок дней просрочки. Здесь то же самое, только вместо квартиры — залоговая вещь, а вместо арендной платы — проценты по займу.

### Как считается строка просрочки

1. Сравниваем календарные даты в **Europe/Moscow** по началу дня.
2. Выкуп **в дату «до» включительно** — просрочки нет (`дниПросрочки = 0`).
3. `дниПросрочки` — сколько полных календарных дней прошло **строго после** даты «до».
4. Тариф задаёт `длинаПериодаПросрочки` (например 1, 2 или 7 дней) и `ставкаПросрочки` — **процент от суммы займа за один такой период**.
5. Число периодов округляется **вверх**: даже один день сверх полного периода открывает новый период. Так ломбард не «дарит» хвост дней.

### Примеры

**Вовремя.** Займ 10 000 ₽, базовая ставка 3,5 %, дата «до» — 10 апреля, выкуп 10 апреля:

- проценты = 10 000 × 3,5 / 100 = **350 ₽**
- просрочки нет
- к оплате = 10 000 + 350 = **10 350 ₽**

**Просрочка, период = 1 день** (подневная). Тариф: ставка просрочки 0,5 %/день. Выкуп 13 апреля → 3 дня после «до» → 3 периода:

- база = 350 ₽
- просрочка = 10 000 × 0,5 / 100 × 3 = **150 ₽**
- к оплате = 10 000 + 350 + 150 = **10 500 ₽**

**Просрочка, период = 7 дней** (недельный блок). Тариф: 0,35 % за каждые 7 дней. Выкуп на 3-й день после «до»:

- дни = 3, периоды = округление вверх(3/7) = **1**
- просрочка = 10 000 × 0,35 / 100 × 1 = **35 ₽**  
  (не 3 × дневная ставка: весь «хвост» до конца первой недели считается одним периодом)

Выкуп на 8-й день: округление вверх(8/7) = **2** периода → 70 ₽ просрочки.

Реализация: `api/src/modules/pledge/services/redemption-calculator.service.ts`.

## DTO

Все контракты API в `shared/dto` по доменам: form/query DTO с Yup + find/response интерфейсы + enums. API: `YupValidationPipe`. Web: `yupDtoFieldRules` / `Dto.parse`. Билдер `Dto.create` / `partial` / `union` + `nested`, авто-`trim` строк, обязательный `label`.

CI: параллельные пути **backend** и **frontend**, этапы **test → build → deploy**.

## Что упрощено / как доделать

- sqljs в тестах не повторяет PG ENUM/схемы один в один (`EnumColumn` / `JsonColumn` / без schema).
- Нет аутентификации / ролей / аудита операций.
- Можно добавить отдельный e2e-тест на реальном Postgres в CI (например, development-стенд).
- UI можно усилить валидацией характеристик строго по схеме категории на клиенте.
